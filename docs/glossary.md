# Glossary

**Compiled:** 2026-10-16. External sources were accessed on 2026-10-16 unless a different date is given.
**Scope:** The technical terms that [README.md](../README.md) and the research documents in `docs/*.md` rely on. The raw data in the paper and news corpora is not covered. The glossary records how the repository *uses* each term today. It does not change or settle the meaning in the source documents. Where documents disagree, see [Inconsistent usage found](#inconsistent-usage-found).
**Status:** Research and design only. A term listed here does not mean that anything has been implemented.

**Status tags**

- **[standard term]**: defined normatively by a published specification, RFC, W3C or NIST document, or by the primary documentation of the named technology. The definition gives that source's meaning. The repository may apply it more narrowly.
- **[research term]**: established in scholarly or industry literature but without one normative definition. The meaning can vary by author or vendor.
- **[project working definition]**: coined or scoped by this repository. **It is not an industry standard.** The cited source is the repository document that defines it.

Corpus IDs (AMP-xxx, AMN-xxx) refer to [paper-corpus/papers.jsonl](paper-corpus/papers.jsonl) and [news-corpus/news.jsonl](news-corpus/news.jsonl). Cite the original publication, not the corpus summary.

### A2A (Agent2Agent protocol)
**[standard term]** An open protocol for communication between independently hosted agents. It covers discovery through Agent Cards, messages, Tasks, Artifacts and streaming updates. The repository treats it as the *delegation* interface, not as a checkpoint or migration standard.
**Source:** [A2A v1.0.0 specification](https://a2a-protocol.org/v1.0.0/specification/); AMN-005 (announcement), AMN-071 (v1.0 release).
**See:** [README](../README.md), [research-landscape](research-landscape.md), [how-it-works](how-it-works.md), [open-questions](open-questions.md)

### A2A Artifact
**[standard term]** "An output (e.g., a document, image, structured data) generated by the agent" as the result of a Task (A2A §2.2). An Artifact is made of Parts.
**Source:** [A2A v1.0.0 §2.2](https://a2a-protocol.org/v1.0.0/specification/).
**See:** [README](../README.md), [how-it-works](how-it-works.md), [roadmap](roadmap.md)

### A2A context ID (`contextId`)
**[standard term]** An identifier that logically groups several related Tasks and Messages (A2A §3.4.1). It is local to the A2A interaction. It is not a global agent identity and it is not a security proof.
**Source:** [A2A v1.0.0 §3.4.1](https://a2a-protocol.org/v1.0.0/specification/).
**See:** [forensics](agent-forensics-and-fingerprints.md)

### A2A Task
**[standard term]** "The fundamental unit of work managed by A2A, identified by a unique ID" (A2A §2.2). A Task has a lifecycle with these states: submitted, working, input-required, auth-required, completed, failed, canceled and rejected (§4.1.3). The server issues the Task ID, so the receiver's Task ID is not necessarily the origin's logical task ID. Do not confuse an A2A Task with the separate MCP *Tasks* extension.
**Source:** [A2A v1.0.0 §2.2, §4.1.3](https://a2a-protocol.org/v1.0.0/specification/).
**See:** [forensics](agent-forensics-and-fingerprints.md), [open-questions](open-questions.md), [security-and-trust](security-and-trust.md)

### AG-UI (Agent-User Interaction protocol)
**[standard term]** "An open, lightweight, event-based protocol that standardizes how AI agents connect to user-facing applications." The repository uses it for user-visible streaming, approvals and state synchronization, not for transfer between agents.
**Source:** [ag-ui-protocol/ag-ui](https://github.com/ag-ui-protocol/ag-ui); AMN-010, AMN-096.
**See:** [README](../README.md), [research-landscape](research-landscape.md), [how-it-works](how-it-works.md)

### Agent Card
**[standard term]** "A JSON metadata document published by an A2A Server, describing its identity" plus its capabilities, skills, endpoint and authentication requirements (A2A §2.2). An Agent Card advertises; it is not proof of trust. Forged and poisoned Agent Cards are documented threats (AMN-072).
**Source:** [A2A v1.0.0 §2.2](https://a2a-protocol.org/v1.0.0/specification/); AMN-072.
**See:** [how-it-works](how-it-works.md), [security-and-trust](security-and-trust.md), [open-questions](open-questions.md)

### Agent definition
**[project working definition]** The declared, versioned design of an agent: model selection, system instructions, permitted tools, workflow and policies. Many instances can share one definition. Sharing a definition does not make two instances the same agent.
**Source:** project working definition, [movement-vs-copy §2](agent-movement-vs-copy-replication-multiplication.md) and [forensics: identity and lineage model](agent-forensics-and-fingerprints.md) (`agent_definition_id`).
**See:** [open-questions](open-questions.md) (AM-01), [device-matrix](device-compatibility-and-capability-matrix.md)

### Agent instance
**[project working definition]** A concrete running instance, container or process of an agent definition. Its ID changes on restart. It is distinct from both the definition and the logical task.
**Source:** project working definition, [forensics](agent-forensics-and-fingerprints.md) (`agent_instance_id`).
**See:** [movement-vs-copy](agent-movement-vs-copy-replication-multiplication.md), [open-questions](open-questions.md) (AM-02)

### Agent movement
**[project working definition]** The project's proposed name for studying how an AI-agent task or execution can move between agents, frameworks, models, machines and organizations without losing relevant context, accountability or safety controls. **It is not a recognized standard** ([README](../README.md) says so explicitly). Documents disagree on whether delegation counts as movement (see below).
**Source:** project working definition, [README](../README.md); narrower variants in [open-questions](open-questions.md) and [how-it-works](how-it-works.md).
**See:** all documents

### Agent Spec (Open Agent Specification)
**[research term]** A declarative, framework-agnostic language for defining agents and agentic workflows once and running them on several runtimes. It is prior work on *definition portability*, which is a different claim from restoring in-flight execution.
**Source:** AMP-059 ([arXiv:2510.04173](https://arxiv.org/abs/2510.04173)); AMN-060.
**See:** [open-questions](open-questions.md)

### Attestation
**[standard term]** with several meanings. NIST's glossary lists multiple definitions, from signed hardware measurements to "the issue of a statement … that fulfillment of specified requirements has been demonstrated". In SPIRE, attestation is "asserting the identity of a workload" (node and workload attestation). in-toto attestations are "verifiable claims about any aspect of how a piece of software is produced". The repository uses all three meanings and also an informal one (see the inconsistencies section).
**Source:** [NIST CSRC glossary: attestation](https://csrc.nist.gov/glossary/term/attestation); [SPIRE concepts](https://spiffe.io/docs/latest/spire-about/spire-concepts/); [in-toto attestation framework](https://github.com/in-toto/attestation).
**See:** [forensics](agent-forensics-and-fingerprints.md), [device-matrix](device-compatibility-and-capability-matrix.md), [top-20](top-20-human-impact-questions-for-agentic-ai.md)

### Audience (token audience)
**[standard term]** In OAuth 2.0 Token Exchange, `audience` is "the logical name of the target service where the client intends to use the requested security token" (RFC 8693 §2.1). The repository's "audience-bound grants" are tokens that are valid only at the intended destination.
**Source:** [RFC 8693 §2.1](https://www.rfc-editor.org/rfc/rfc8693).
**See:** [security-and-trust](security-and-trust.md), [open-questions](open-questions.md) (AM-05), [forensics](agent-forensics-and-fingerprints.md)

### Baggage (W3C)
**[standard term]** A standard for "representing and propagating a set of application-defined properties associated with a distributed request or workflow execution". Its keys and values can reach other systems, so the repository forbids putting secrets or personal data in it. Status: W3C Candidate Recommendation Snapshot (30 May 2024).
**Source:** [W3C Baggage](https://www.w3.org/TR/baggage/).
**See:** [forensics](agent-forensics-and-fingerprints.md)

### Canonicalization (JSON Canonicalization Scheme, JCS)
**[standard term]** A deterministic representation of JSON data that makes hashing and signing "reliably repeatable". The repository suggests it for movement receipts. Note that RFC 8785 is an *Informational* RFC (Independent Submission), not a Standards Track document.
**Source:** [RFC 8785](https://www.rfc-editor.org/rfc/rfc8785.html).
**See:** [forensics](agent-forensics-and-fingerprints.md)

### Chain of custody
**[standard term]** "A process that tracks the movement of evidence through its collection, safeguarding, and analysis lifecycle by documenting each person who handled the evidence, the date/time it was collected or transferred, and the purpose for the transfer."
**Source:** [NIST CSRC glossary: chain of custody](https://csrc.nist.gov/glossary/term/chain_of_custody) (NIST SP 800-72, SP 800-101 Rev. 1); [NIST SP 800-86](https://csrc.nist.gov/pubs/sp/800/86/final).
**See:** [forensics](agent-forensics-and-fingerprints.md)

### Checkpoint
**[standard term]**, defined per technology. In LangGraph, checkpointers "persist a thread's graph state as checkpoints" (graph-state snapshots). In CRIU, a checkpoint is a process-level snapshot. A checkpoint in one runtime cannot be assumed to restore in another. The repository's *application checkpoint* is a portable, approved application-level snapshot (a project working definition).
**Source:** [LangGraph persistence](https://docs.langchain.com/oss/python/langgraph/persistence); [CRIU](https://criu.org/Main_Page); AMP-048 (CRIUgpu), AMP-070 (ACRFence: the risks of checkpoint-restore in agent frameworks).
**See:** [README](../README.md), [movement-vs-copy](agent-movement-vs-copy-replication-multiplication.md), [open-questions](open-questions.md) (AM-07), [roadmap](roadmap.md)

### Checkpoint relocation (runtime relocation, task relocation "M")
**[project working definition]** Stop at a safe boundary, persist a runtime-compatible application checkpoint, restore it on another worker, fence the old executor, and reconcile uncertain external effects. The logical task ID is kept, and a new execution ID is issued. The repository says this is substantially harder than delegation.
**Source:** project working definition, [README](../README.md) (item 3), [movement-vs-copy §1](agent-movement-vs-copy-replication-multiplication.md), [device-matrix](device-compatibility-and-capability-matrix.md) ("M").
**See:** [research-landscape](research-landscape.md), [roadmap](roadmap.md) (Phase 2), [open-questions](open-questions.md) (E2)

### Clone (snapshot clone)
**[project working definition]** Create a new agent with a **new** identity from an explicitly authorized, exportable application snapshot, recording lineage back to the source. The two agents can diverge immediately. A clone is not a move.
**Source:** project working definition, [movement-vs-copy §3](agent-movement-vs-copy-replication-multiplication.md).
**See:** [forensics](agent-forensics-and-fingerprints.md) (`lineage_relation`), [open-questions](open-questions.md) (AM-12)

### Compatibility negotiation
**[project working definition]** Before a transfer, the parties agree on envelope schema version, required and optional capabilities, tool preconditions, degraded-mode semantics and acceptable loss. They refuse when critical constraints are not supported.
**Source:** project working definition, [how-it-works](how-it-works.md) (step 3), [open-questions](open-questions.md) (AM-11).
**See:** [research-landscape](research-landscape.md), [roadmap](roadmap.md) (Phase 3)

### Compensation (compensating action)
**[research term]** An action that semantically undoes a completed step when a long-running transaction cannot be rolled back atomically. The concept comes from the saga model. The repository uses "compensation" once, as one of the human-control checkpoints, and does not use the word "saga".
**Source:** Garcia-Molina & Salem, "Sagas", SIGMOD 1987, [doi:10.1145/38713.38742](https://doi.org/10.1145/38713.38742).
**See:** [top-20](top-20-human-impact-questions-for-agentic-ai.md) (HQ-01)

### Content digest (message digest, hash)
**[standard term]** "The result of applying a hash function to a message." In the repository, a digest proves consistency with a trusted reference value. It does not prove authorship, correctness or that the content is benign.
**Source:** [NIST CSRC glossary: message digest](https://csrc.nist.gov/glossary/term/message_digest) (FIPS 186-5).
**See:** [forensics](agent-forensics-and-fingerprints.md), [security-and-trust](security-and-trust.md), [how-it-works](how-it-works.md)

### Continuation contract
**[project working definition]**, labelled in the repository as an interpretation. A hypothesized verifiable bundle of portable allowed state, versioned capabilities, authority transfer, an external-effect ledger and measurable continuity.
**Source:** project working definition, [open-questions](open-questions.md) ("Evidence" section).
**See:** [top-20](top-20-human-impact-questions-for-agentic-ai.md) ("human-authority-preserving handoff")

### Copy (definition copy, "C")
**[project working definition]** Start a new, independent agent instance from the same agent definition. The new instance gets a different instance ID. Copying does **not** copy in-progress conversation, state, memory or credentials.
**Source:** project working definition, [movement-vs-copy §2](agent-movement-vs-copy-replication-multiplication.md); [device-matrix](device-compatibility-and-capability-matrix.md) ("C").
**See:** [open-questions](open-questions.md) (AM-12)

### Cross-framework migration (cross-framework reconstruction)
**[project working definition]** Rebuild a workflow on a different runtime or framework using an adapter and a portable representation, with explicitly documented loss of features. It is not byte-for-byte state transfer.
**Source:** project working definition, [README](../README.md) (item 4); [open-questions](open-questions.md) (E3, "cross-framework reconstruction").
**See:** [top-20](top-20-human-impact-questions-for-agentic-ai.md) (HQ-19), [roadmap](roadmap.md) (Phase 3)

### Delegation
**[research term]** One agent asks another to perform a task. The delegator normally keeps oversight and need not expose or move its internals. In the literature, delegation also transfers authority, responsibility and accountability (AMP-067). It has roots in Contract Net task allocation (AMP-001). RFC 8693 separately distinguishes *delegation* (the actor keeps its own identity) from *impersonation*.
**Source:** AMP-001, AMP-044, AMP-067; [RFC 8693 §1.1](https://www.rfc-editor.org/rfc/rfc8693); project scoping in [README](../README.md) (item 1) and [movement-vs-copy](agent-movement-vs-copy-replication-multiplication.md).
**See:** [research-landscape](research-landscape.md), [roadmap](roadmap.md) (Phase 1), [open-questions](open-questions.md) (E1)

### Durable execution
**[research term]**, used by vendors without a single normative definition. Execution whose progress is persisted, for example as an event history or step checkpoints, so that it resumes after crashes or restarts. In Temporal, "a Workflow Execution is a durable, reliable, and scalable function execution" that resumes through *replay* against its Event History.
**Source:** [Temporal: Workflow Execution](https://docs.temporal.io/workflow-execution); AMP-019 (DBOS); AMN-055, AMN-077, AMN-099.
**See:** [README](../README.md), [research-landscape](research-landscape.md), [roadmap](roadmap.md) (Phase 2), [open-questions](open-questions.md)

### Evidence grades (E0–E3)
**[project working definition]** The repository's proposed, non-standard grading of forensic evidence. E3 is cryptographically corroborated, E2 is corroborated operational records, E1 is correlated self-reported telemetry, and E0 is inference only. The grades are not probabilities.
**Source:** project working definition, [forensics](agent-forensics-and-fingerprints.md).
**See:** [forensics](agent-forensics-and-fingerprints.md)

### Exactly-once, at-least-once, at-most-once
**[research term]** Delivery and execution guarantees. At-least-once may repeat an action on retry, which is safe only for idempotent operations. At-most-once refuses to re-run an interrupted attempt. The repository treats exactly-once external side effects as **unproven** without cooperation from the target system.
**Source:** [AWS Durable Execution SDK: idempotency and retries](https://docs.aws.amazon.com/durable-execution/patterns/best-practices/idempotency/) (cited as [SRC-8] in open-questions).
**See:** [security-and-trust](security-and-trust.md), [open-questions](open-questions.md) (AM-04), [movement-vs-copy](agent-movement-vs-copy-replication-multiplication.md)

### Fencing (fencing token, fencing epoch) and split-brain
**[research term]** A fencing token is a monotonically increasing number, issued with each grant of a lock or lease, that lets a resource reject writes from a holder with a stale token. *Split-brain* is the failure in which two executors both believe they own the same work. The repository's `fencing_epoch` (a monotonic coordinator epoch) is a project field built on this idea.
**Source:** M. Kleppmann, ["How to do distributed locking"](https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html) (2016, practitioner essay; there is no normative standard); project field in [forensics](agent-forensics-and-fingerprints.md).
**See:** [movement-vs-copy](agent-movement-vs-copy-replication-multiplication.md), [open-questions](open-questions.md) (AM-03, E2), [device-matrix](device-compatibility-and-capability-matrix.md)

### Fingerprint (definition, artifact/checkpoint, behavioral)
**[project working definition]** The repository separates three kinds. A *definition/configuration fingerprint* is a hash of the normalized declared configuration, and copies can share it. An *artifact/checkpoint fingerprint* is a content digest of a defined byte representation. A *behavioral fingerprint* is made of noisy observed patterns: weak evidence, never identity proof. "A fingerprint is not necessarily an identity."
**Source:** project working definition, [forensics](agent-forensics-and-fingerprints.md). No public standard defines a universal agent fingerprint (stated in that document).
**See:** [README](../README.md)

### Fork
**[project working definition]** Branch one approved snapshot into several independently evolving branches, keeping parent-child provenance. Merging results back is a separate, domain-specific operation.
**Source:** project working definition, [movement-vs-copy](agent-movement-vs-copy-replication-multiplication.md) ("Related but distinct").
**See:** [forensics](agent-forensics-and-fingerprints.md) (`lineage_relation: fork`), [open-questions](open-questions.md) (AM-12)

### Handoff (weak movement)
**[project working definition]** Hand explicit task context to another agent, which may start its own execution. It is *not* a lossless runtime migration. The repository uses the word both as a synonym of delegation and as "weak movement" (see the inconsistencies section).
**Source:** project working definition, [README](../README.md) (item 1); [movement-vs-copy §1](agent-movement-vs-copy-replication-multiplication.md) ("weak movement / handoff").
**See:** [how-it-works](how-it-works.md), [top-20](top-20-human-impact-questions-for-agentic-ai.md), [forensics](agent-forensics-and-fingerprints.md)

### Handoff envelope (task envelope, movement envelope)
**[project working definition]** A proposed small, versioned, policy-checked package that crosses an agent boundary. It holds the schema version, movement and task IDs, origin and destination, a goal, classified context and artifact references, an optional checkpoint reference, an idempotency key, approval and grant *references* (never raw credentials), a trace context and an integrity digest. **It is a conceptual schema, not a published or interoperable wire format.**
**Source:** project working definition, [how-it-works](how-it-works.md) ("Proposed versioned envelope").
**See:** [README](../README.md), [research-landscape](research-landscape.md), [roadmap](roadmap.md), [open-questions](open-questions.md) (E1)

### Host profile (H0–H4)
**[project working definition]** A normalized candidate *maximum* hosting class for a device. H0 is a peripheral or tool only, H1 a tiny embedded module, H2 a thin client or proxy, H3 an app-class host and H4 a durable compute host. It is not a migration level or a safety ranking.
**Source:** project working definition, [device-matrix](device-compatibility-and-capability-matrix.md); data in [device-targets.csv](../data/device-targets.csv).
**See:** [device-matrix](device-compatibility-and-capability-matrix.md)

### Idempotency and idempotency key
**[standard term]** A request is idempotent "if the intended effect on the server of multiple identical requests … is the same as the effect for a single such request" (RFC 9110 §9.2.2). An *idempotency key* is a client-supplied unique value that lets a server deduplicate retries of non-idempotent operations. Its HTTP header draft (draft-ietf-httpapi-idempotency-key-header) is an **expired Internet-Draft, not an RFC**. Idempotency needs cooperation from the target system.
**Source:** [RFC 9110 §9.2.2](https://www.rfc-editor.org/rfc/rfc9110.html#name-idempotent-methods); [IETF datatracker: Idempotency-Key draft](https://datatracker.ietf.org/doc/draft-ietf-httpapi-idempotency-key-header/).
**See:** [README](../README.md), [how-it-works](how-it-works.md), [open-questions](open-questions.md) (AM-04), [security-and-trust](security-and-trust.md)

### Kubernetes replica / HorizontalPodAutoscaler (HPA)
**[standard term]** A Deployment manages a replicated set of Pods. A HorizontalPodAutoscaler "automatically updates a workload resource … with the aim of automatically scaling capacity to match demand". It scales Pods. It does not create semantically independent agent tasks or transfer application checkpoints.
**Source:** [Kubernetes: HPA](https://kubernetes.io/docs/concepts/workloads/autoscaling/horizontal-pod-autoscale/); [Kubernetes: Deployments](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/).
**See:** [movement-vs-copy](agent-movement-vs-copy-replication-multiplication.md), [research-landscape](research-landscape.md)

### Lease
**[research term]** A time-bounded grant of a right, such as exclusive ownership, that expires unless it is renewed. This bounds how long a failed or partitioned holder can block others. The repository proposes leases for exclusive task ownership during relocation and failover.
**Source:** Gray & Cheriton, "Leases", SOSP 1989, [doi:10.1145/74850.74870](https://doi.org/10.1145/74850.74870).
**See:** [movement-vs-copy](agent-movement-vs-copy-replication-multiplication.md), [device-matrix](device-compatibility-and-capability-matrix.md), [open-questions](open-questions.md) (AM-03)

### Least privilege
**[standard term]** "A security principle that a system should restrict the access privileges of users (or processes acting on behalf of users) to the minimum necessary to accomplish assigned tasks."
**Source:** [NIST CSRC glossary: least privilege](https://csrc.nist.gov/glossary/term/least_privilege) (CNSSI 4009-2022, NIST SP 800-53 Rev. 5).
**See:** [how-it-works](how-it-works.md), [top-20](top-20-human-impact-questions-for-agentic-ai.md), [forensics](agent-forensics-and-fingerprints.md)

### Lineage (lineage relation)
**[project working definition]**, informed by provenance standards. The recorded ancestry between executions and movements: `parent_movement_id`, `parent_execution_id` and a `lineage_relation` taking one of the values delegate, relocate, clone, fork, replicate or fan_out. OpenLineage is noted as reusable for data lineage only.
**Source:** project working definition, [forensics](agent-forensics-and-fingerprints.md); [OpenLineage spec](https://github.com/OpenLineage/OpenLineage/blob/main/spec/OpenLineage.md).
**See:** [movement-vs-copy](agent-movement-vs-copy-replication-multiplication.md), [open-questions](open-questions.md), [top-20](top-20-human-impact-questions-for-agentic-ai.md)

### Live migration (live process migration, strong migration)
**[research term]** Moving a *running* process or virtual machine, including memory, stack, connections and in-flight operations, to another host with minimal interruption. Process migration is surveyed in AMP-013. Pre-copy virtual-machine live migration is described in AMP-015. The repository explicitly **does not claim** live migration across unrelated agent frameworks or model providers.
**Source:** AMP-013 (Milojičić et al. 2000), AMP-015 (Clark et al. 2005), AMP-018; [CRIU](https://criu.org/Main_Page).
**See:** [README](../README.md), [movement-vs-copy](agent-movement-vs-copy-replication-multiplication.md), [research-landscape](research-landscape.md), [device-matrix](device-compatibility-and-capability-matrix.md) ("L")

### Logical task ID
**[project working definition]** An application-assigned identifier that stays stable while a task moves across agents and executions. Each execution and A2A Task gets its own ID.
**Source:** project working definition, [forensics](agent-forensics-and-fingerprints.md) (`logical_task_id`); [movement-vs-copy §1](agent-movement-vs-copy-replication-multiplication.md).
**See:** [open-questions](open-questions.md) (AM-02), [device-matrix](device-compatibility-and-capability-matrix.md)

### Loss report (lossy-state report)
**[project working definition]** An explicit, field-level record of which state was kept, removed or lost when a task continues on a different runtime or model.
**Source:** project working definition, [open-questions](open-questions.md) (AM-07, AM-11).
**See:** [roadmap](roadmap.md) (Phase 3), [movement-vs-copy](agent-movement-vs-copy-replication-multiplication.md), [top-20](top-20-human-impact-questions-for-agentic-ai.md)

### MCP (Model Context Protocol)
**[standard term]** "An open protocol that enables seamless integration between LLM applications and external data sources and tools." It uses JSON-RPC 2.0 with "stateless, self-contained requests" in the 2026-07-28 revision. Long-running Tasks are an opt-in extension. MCP is not a protocol for transferring agent execution, and a stateless transport does not make the agent stateless.
**Source:** [MCP specification 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28); AMN-001, AMN-088.
**See:** [README](../README.md), [research-landscape](research-landscape.md), [open-questions](open-questions.md), [security-and-trust](security-and-trust.md)

### MCP host, client and server
**[standard term]** *Hosts* are "LLM applications that initiate connections". *Clients* are "connectors within the host application". *Servers* are "services that provide context and capabilities".
**Source:** [MCP specification 2026-07-28, Overview](https://modelcontextprotocol.io/specification/2026-07-28).
**See:** [research-landscape](research-landscape.md), [sources](sources.md)

### MCP tools, resources and prompts
**[standard term]** These are the server features. *Tools* are "functions for the AI model to execute", *resources* are "context and data, for the user or the AI model to use", and *prompts* are "templated messages and workflows for users". The spec states that tool descriptions should be considered untrusted unless they come from a trusted server.
**Source:** [MCP specification 2026-07-28, Features; Tool Safety](https://modelcontextprotocol.io/specification/2026-07-28); AMN-003 (tool poisoning).
**See:** [research-landscape](research-landscape.md), [how-it-works](how-it-works.md), [device-matrix](device-compatibility-and-capability-matrix.md)

### Movement graph
**[project working definition]** An evidence-based graph of who started a task, which verified executor accepted it, what was touched, copied, delegated or resumed, and which artifacts and effects resulted, with the source and uncertainty of each item.
**Source:** project working definition, [forensics](agent-forensics-and-fingerprints.md).
**See:** [forensics](agent-forensics-and-fingerprints.md)

### Movement ID
**[project working definition]** A new, globally unique identifier for each proposed source-to-destination transition. It is chained by `parent_movement_id`.
**Source:** project working definition, [forensics](agent-forensics-and-fingerprints.md) (`movement_id`); [how-it-works](how-it-works.md) envelope.
**See:** [forensics](agent-forensics-and-fingerprints.md)

### Multiplication (agent multiplication, spawning, fan-out)
**[project working definition]**. "Agent multiplication" is an **informal project term**. The conventional concepts are dynamic spawning, fan-out, worker-pool scaling and multi-agent orchestration. A coordinator creates a bounded number of child agents or tasks, each a separate execution, and then aggregates their results.
**Source:** project working definition, [movement-vs-copy §5](agent-movement-vs-copy-replication-multiplication.md).
**See:** [open-questions](open-questions.md) (AM-12), [top-20](top-20-human-impact-questions-for-agentic-ai.md) (HQ-18)

### OCI image
**[standard term]** "An OCI Image, consisting of an image manifest, an image index (optional), a set of filesystem layers, and a configuration." It makes *deployment* portable. It does not carry agent state, memory or identity.
**Source:** [OCI Image Format Specification](https://specs.opencontainers.org/image-spec/) (spec.md, v1.1.1).
**See:** [README](../README.md), [research-landscape](research-landscape.md), [device-matrix](device-compatibility-and-capability-matrix.md)

### OpenTelemetry GenAI semantic conventions (span, trace)
**[standard term]** OpenTelemetry conventions for spans, metrics and events from generative-AI clients, agents and tools, now maintained in a dedicated repository. The repository uses them for correlation, not for tamper-proof audit or identity. The maintained repository did not state a stability level when it was checked on 2026-10-16.
**Source:** [OTel GenAI semconv](https://opentelemetry.io/docs/specs/semconv/gen-ai/); [semantic-conventions-genai repository](https://github.com/open-telemetry/semantic-conventions-genai); AMN-054.
**See:** [README](../README.md), [forensics](agent-forensics-and-fingerprints.md), [research-landscape](research-landscape.md)

### Operation ID
**[project working definition]** A stable identifier for each transfer event or externally visible action. Retries and reconciliation use it to detect duplicates. The repository uses it alongside, but separately from, the idempotency key.
**Source:** project working definition, [roadmap](roadmap.md) (Movement SDK, Phase 1); [movement-vs-copy](agent-movement-vs-copy-replication-multiplication.md) (P0).
**See:** [security-and-trust](security-and-trust.md), [open-questions](open-questions.md), [top-20](top-20-human-impact-questions-for-agentic-ai.md)

### Partial deployment ("P")
**[project working definition]** Install a narrowly scoped module on a target device, such as a tool proxy, a perception or policy filter, a planner or an inference service. The module has its own lifecycle.
**Source:** project working definition, [device-matrix](device-compatibility-and-capability-matrix.md).
**See:** [device-matrix](device-compatibility-and-capability-matrix.md)

### Policy decision (policy decision point, OPA)
**[standard term]** A policy decision point "computes access decisions by evaluating the applicable digital policies" (NIST SP 800-162). Open Policy Agent "decouples policy decision-making from policy enforcement". The repository's `policy_decision_ref` points to such a decision record.
**Source:** [NIST CSRC glossary: policy decision point](https://csrc.nist.gov/glossary/term/policy_decision_point) (NIST SP 800-162, SP 800-95); [OPA documentation](https://www.openpolicyagent.org/docs).
**See:** [README](../README.md), [forensics](agent-forensics-and-fingerprints.md), [roadmap](roadmap.md)

### Portable task context
**[project working definition]** An explicit, policy-checked package of goals, inputs and artifact references, plus resumable checkpoints when supported, that can cross an agent boundary.
**Source:** project working definition, [README](../README.md) (item 2).
**See:** [movement-vs-copy](agent-movement-vs-copy-replication-multiplication.md), [top-20](top-20-human-impact-questions-for-agentic-ai.md)

### Prompt injection (indirect prompt injection, tool poisoning)
**[standard term]**, with OWASP as the reference definition. A prompt injection occurs "when user prompts alter the LLM's behavior or output in unintended ways". *Indirect* injections come through external content such as websites, files, tool output or Agent Cards. *Tool poisoning* hides instructions in MCP tool metadata.
**Source:** [OWASP LLM01:2025 Prompt Injection](https://genai.owasp.org/llmrisk/llm01-prompt-injection/); AMP-025, AMP-031, AMP-039; AMN-003, AMN-072.
**See:** [security-and-trust](security-and-trust.md), [open-questions](open-questions.md), [top-20](top-20-human-impact-questions-for-agentic-ai.md) (HQ-04)

### Provenance
**[standard term]** "Information about entities, activities, and people involved in producing a piece of data or thing" (W3C PROV-DM). The repository applies it to data, tools, artifacts, checkpoints and model-dependent decisions.
**Source:** [W3C PROV-DM](https://www.w3.org/TR/prov-dm/).
**See:** [how-it-works](how-it-works.md), [forensics](agent-forensics-and-fingerprints.md), [open-questions](open-questions.md), [top-20](top-20-human-impact-questions-for-agentic-ai.md)

### Receipt (dispatch receipt, acceptance receipt)
**[project working definition]** A signed record over canonicalized, non-sensitive metadata and a digest of the approved envelope. The origin emits one on dispatch and the recipient emits a separate one on acceptance or rejection. Comparing the pair establishes a mutually acknowledged hop. A missing receipt leaves the state unknown.
**Source:** project working definition, [forensics](agent-forensics-and-fingerprints.md).
**See:** [forensics](agent-forensics-and-fingerprints.md)

### Reconciliation and the "unknown/reconcile" state
**[project working definition]** After a timeout or partition, query the actual task and target-system status instead of blindly retrying. Outcomes that remain ambiguous are recorded as **unknown/reconcile**, which is neither success nor failure.
**Source:** project working definition, [how-it-works](how-it-works.md) (step 8); [roadmap](roadmap.md) (Phase 2); [open-questions](open-questions.md) (AM-04).
**See:** [security-and-trust](security-and-trust.md), [forensics](agent-forensics-and-fingerprints.md), [top-20](top-20-human-impact-questions-for-agentic-ai.md)

### Remote use ("R")
**[project working definition]** The origin stays in place and calls an approved capability on a device or gateway. Explicitly *not movement*.
**Source:** project working definition, [device-matrix](device-compatibility-and-capability-matrix.md).
**See:** [device-matrix](device-compatibility-and-capability-matrix.md)

### Replication (agent replication; active/passive, active/active)
**[project working definition]**, adapting conventional distributed-systems terms. A controller keeps the desired number of equivalent agent workers for one logical service, for availability or throughput. In *active/passive* replication, one replica writes, and a standby takes over after failover from durable state. In *active/active* replication, several replicas work at the same time, which needs partitioning and a conflict policy. Replicating container processes is not replicating conversational memory, workflow ownership or side effects.
**Source:** project working definition, [movement-vs-copy §4](agent-movement-vs-copy-replication-multiplication.md).
**See:** [research-landscape](research-landscape.md), [open-questions](open-questions.md) (AM-12), [top-20](top-20-human-impact-questions-for-agentic-ai.md) (HQ-18)

### Safe boundary
**[project working definition]** A point in execution at which a checkpoint can be taken and resumed elsewhere without leaving partially applied side effects that cannot be reconciled.
**Source:** project working definition, [README](../README.md) (item 3); [how-it-works](how-it-works.md) (step 5).
**See:** [device-matrix](device-compatibility-and-capability-matrix.md), [open-questions](open-questions.md) (E2)

### Semantic compatibility (semantic continuity)
**[project working definition]** Whether a destination runtime or model actually understands and preserves the intent, policies, constraints and quality expectations of unfinished work. Schema and version match alone do not establish it.
**Source:** project working definition, [open-questions](open-questions.md) (AM-08, AM-11); related cross-agent study cited there as [SRC-7].
**See:** [README](../README.md), [top-20](top-20-human-impact-questions-for-agentic-ai.md) (HQ-19)

### Side-effect ledger (effect ledger)
**[project working definition]** A durable record of intended, committed and uncertain external effects, keyed by operation or effect ID. Ideally it is confirmed on the target side. It is used to prevent and detect duplicate actions after handoff or restore.
**Source:** project working definition, [open-questions](open-questions.md) ("continuation contract", E2); [forensics](agent-forensics-and-fingerprints.md). Comparable research mechanism: AMP-070 (recording irreversible tool effects).
**See:** [top-20](top-20-human-impact-questions-for-agentic-ai.md) (HQ-19)

### SPIFFE, SPIFFE ID and trust domain
**[standard term]** SPIFFE is a standard for workload identity. A *SPIFFE ID* "is a string that uniquely and specifically identifies a workload". The *trust domain* "corresponds to the trust root of a system". SPIRE is its reference implementation.
**Source:** [SPIFFE concepts](https://spiffe.io/docs/latest/spiffe-about/spiffe-concepts/); [SPIRE concepts](https://spiffe.io/docs/latest/spire-about/spire-concepts/).
**See:** [README](../README.md), [forensics](agent-forensics-and-fingerprints.md), [roadmap](roadmap.md) (Phase 4), [security-and-trust](security-and-trust.md)

### Strong and weak mobility (code mobility)
**[research term]** In the code-mobility literature, *strong mobility* moves code **and** execution state, such as the stack and instruction pointer. *Weak mobility* moves code and possibly data, and execution restarts at the destination. The repository's "strong migration" and "weak movement" are analogous to these terms but are not defined identically.
**Source:** AMP-008 (Fuggetta, Picco & Vigna, "Understanding code mobility", IEEE TSE 1998, [doi:10.1109/32.685258](https://doi.org/10.1109/32.685258)). This entry's wording follows the later restatement by [Carzaniga, Picco & Vigna (ICSE 2007)](https://sites.cs.ucsb.edu/~vigna/publications/2007_carzaniga_picco_vigna_ICSE.pdf), because the 1998 full text was not retrieved.
**See:** [research-landscape](research-landscape.md), [movement-vs-copy](agent-movement-vs-copy-replication-multiplication.md), [sources](sources.md)

### SVID (SPIFFE Verifiable Identity Document)
**[standard term]** "The document with which a workload proves its identity to a resource or caller", for example an X.509 certificate used in mTLS. It authenticates a *workload*, not a logical agent or model.
**Source:** [SPIFFE concepts](https://spiffe.io/docs/latest/spiffe-about/spiffe-concepts/); [SPIFFE: working with SVIDs](https://spiffe.io/docs/latest/deploying/svids/).
**See:** [forensics](agent-forensics-and-fingerprints.md)

### Swarm
**[project working definition]** A coordination pattern among several distinct agents that exchange results. The agents need not be copies or replicas.
**Source:** project working definition, [movement-vs-copy](agent-movement-vs-copy-replication-multiplication.md).
**See:** [movement-vs-copy](agent-movement-vs-copy-replication-multiplication.md)

### Token exchange (OAuth 2.0; subject token, actor token)
**[standard term]** A protocol for obtaining security tokens from an OAuth 2.0 authorization server, "including security tokens employing impersonation and delegation". The `subject_token` represents the party on whose behalf the request is made. The optional `actor_token` represents the acting party. The repository relies on it for scoped, short-lived re-issuance of grants instead of forwarding raw credentials. On its own, token exchange does not establish trust in a delegation.
**Source:** [RFC 8693 (Abstract, §1.1, §2.1)](https://www.rfc-editor.org/rfc/rfc8693); AMP-017 (OAuth 2.0 formal analysis), AMP-044.
**See:** [README](../README.md), [research-landscape](research-landscape.md), [security-and-trust](security-and-trust.md), [movement-vs-copy](agent-movement-vs-copy-replication-multiplication.md)

### Trace context (`traceparent`)
**[standard term]** W3C standard HTTP headers that propagate request context for distributed tracing. `traceparent` has the fields version, trace-id, parent-id and trace-flags. The repository is explicit that trace context provides correlation, **not** credentials or proof of identity. Status: W3C Recommendation (23 November 2021).
**Source:** [W3C Trace Context](https://www.w3.org/TR/trace-context/).
**See:** [how-it-works](how-it-works.md) (envelope), [forensics](agent-forensics-and-fingerprints.md)

### Workload identity (workload principal)
**[standard term]** An identity issued to a running software workload, not to a human. SPIFFE defines a workload as "a single piece of software, deployed with a particular configuration for a single purpose". The repository's `workload_principal` records such an identity together with its issuer or trust domain and the verification result.
**Source:** [SPIFFE concepts](https://spiffe.io/docs/latest/spiffe-about/spiffe-concepts/); project field in [forensics](agent-forensics-and-fingerprints.md); AMN-093 (draft ODIS work linking principal, delegated authority and agent instance).
**See:** [README](../README.md), [device-matrix](device-compatibility-and-capability-matrix.md), [sources](sources.md)

## Inconsistent usage found

The following conflicts were observed in the documents at commit `d9a1423`. The source files have **not** been edited. File paths are relative to the repository root.

1. **Is delegation a kind of "movement"?**
   - It is one of the four movement operations in `README.md:11-13`.
   - The envelope in `docs/how-it-works.md:26` uses `"operation": "delegate"`, and `docs/agent-forensics-and-fingerprints.md:57` treats `delegate` as a movement lineage relation.
   - `docs/research-landscape.md:3,7` lists delegation as one of "five different notions of movement".
   - It is separated from movement in `docs/agent-movement-vs-copy-replication-multiplication.md:11-12` (separate rows) and `:64` ("Related but distinct").
   - It is excluded in `docs/device-compatibility-and-capability-matrix.md:80` ("Delegation rather than full movement").
   - `docs/open-questions.md:11` defines movement as a "transfer of task ownership", which ordinary delegation does not do.
2. **Are copy, replication and multiplication kinds of movement?** `docs/research-landscape.md:3,8-9` lists "Copy / replication" and "Multiplication / scaling" as "notions of movement". `docs/agent-movement-vs-copy-replication-multiplication.md:25` says these words must not be used interchangeably, and `docs/open-questions.md:41` (AM-12) says of these operations "None is automatically a move".
3. **Copy vs replication.** `docs/research-landscape.md:8` merges "Copy / replication" into one mode. `docs/agent-movement-vs-copy-replication-multiplication.md:15,17,38-54` defines them as different primitives: an independent instance from a definition, and N managed instances of one logical service.
4. **"Handoff" has two meanings.** It is a synonym of delegation in `README.md:13` ("Delegation / handoff") and `docs/agent-movement-vs-copy-replication-multiplication.md:11` ("Task delegation / handoff"). It is a form of movement in `docs/agent-movement-vs-copy-replication-multiplication.md:31` ("Weak movement / handoff"). `docs/device-compatibility-and-capability-matrix.md:108` uses it for checkpoint transfer ("app checkpoint handoff").
5. **"Migration" for lossy reconstruction vs live state transfer.** `README.md:16` calls lossy adapter-based reconstruction "Cross-framework migration". `README.md:18`, `README.md:68`, `docs/device-compatibility-and-capability-matrix.md:101` ("never falsely label it migration") and `docs/open-questions.md:108` ("cross-framework reconstruction") reserve or avoid "migration" for stronger claims. `docs/top-20-human-impact-questions-for-agentic-ai.md:159` uses "cross-framework migration" again.
6. **Several names for one envelope.** "portable handoff envelope" (`README.md:33`), "Portable task envelope" (`README.md:41`), "task envelope" (`README.md:68`, `docs/research-landscape.md:54`, `docs/roadmap.md:5`, `docs/open-questions.md:75`), "versioned envelope" (`docs/how-it-works.md:20`), "movement envelope" (`docs/sources.md:22`) and "policy envelope" (`docs/top-20-human-impact-questions-for-agentic-ai.md:176`). "Envelope" also has unrelated meanings: "resource envelope" (`docs/device-compatibility-and-capability-matrix.md:17`) and "runtime safety envelopes" (`docs/top-20-human-impact-questions-for-agentic-ai.md:125`).
7. **Several names for relocation.** "Runtime relocation" (`README.md:15`), "Checkpoint relocation / resume" (`docs/agent-movement-vs-copy-replication-multiplication.md:13`), "Checkpoint-resume relocation" (`docs/research-landscape.md:10`), "Task relocation (M)" (`docs/device-compatibility-and-capability-matrix.md:11`), and "checkpoint migration" (`docs/roadmap.md:72`, `docs/open-questions.md:78`). The descriptions match closely, but readers cannot tell whether these names mean the same thing.
8. **Does portable task context include checkpoints?** `README.md:14` includes "resumable checkpoints" in portable task context. `docs/open-questions.md:25` (AM-01) asks for *separate* contracts for a delegated task and a resumable checkpoint, and `docs/device-compatibility-and-capability-matrix.md:80,82` lists task intent and workflow checkpoint as separate components.
9. **Clone vs fork are defined in terms of each other.** `docs/agent-movement-vs-copy-replication-multiplication.md:16` says clone = "Fork a permitted … snapshot into a new identity". `:65` says fork = "Clone an approved snapshot into independent branches". `docs/agent-forensics-and-fingerprints.md:57` treats `clone` and `fork` as distinct lineage values.
10. **"Attestation" has several meanings.** Workload-identity attestation (SPIRE) and supply-chain attestation (in-toto/Sigstore) appear in `docs/agent-forensics-and-fingerprints.md:224,226`. A generic signing sense appears in `docs/device-compatibility-and-capability-matrix.md:52`. "Capability attestation" appears in `docs/top-20-human-impact-questions-for-agentic-ai.md:53` and "retention/deletion attestations" in `docs/top-20-human-impact-questions-for-agentic-ai.md:65`; neither is defined. `docs/agent-forensics-and-fingerprints.md:197` uses "public attestations" in yet another sense.
11. **Outcome state vocabulary differs.** `docs/security-and-trust.md:31` uses request received / accepted / executing / completed / failed / canceled / **unknown**. `docs/open-questions.md:100` uses *complete* / failed / canceled / **unknown/reconcile**. `docs/roadmap.md:40` uses "unknown/reconcile". A2A v1.0 has its own set of task states (see [A2A Task](#a2a-task)).
12. **Colliding labels.** The same short codes mean different things in different documents:
