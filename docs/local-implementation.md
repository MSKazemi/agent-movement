# Local mobility proof of concept (2026-10-15)

**Status:** Tested experimental software. **Not A2A-compatible; not cross-framework reconstruction; not production-secure.** This first executable slice implements only a small, synthetic, local, out-of-process delegation and a separate simulated fenced-effect experiment. Later slices build on it as optional experiments: the [A2A v1 adapter](a2a-adapter.md), [peer authentication](peer-authentication.md), [checkpoint relocation](checkpoint-relocation.md), [signed movement receipts](movement-receipts.md) and [MobilityBench v0.1](mobilitybench-v0.1.md).

## Why start here?

The existing docs describe movement, replication, state transfer, security and device requirements, but do not contain a runnable reference. The first falsifiable claim is intentionally narrow: *an origin process can request a preapproved pure task from a receiver process on loopback, obtain a reproducible artifact receipt, reject unapproved requests, and replay the same delivery without executing the task again*. A separate test checks that a durable SQLite fencing epoch protects **a cooperative, simulated effect gateway** from stale executors.

This is an experimental application profile. It is NOT a substitute for [A2A v1.0](https://a2a-protocol.org/v1.0.0/specification/) and deliberately does not advertise A2A Agent Cards or protocol compatibility. The [official Python SDK](https://github.com/a2aproject/a2a-python) is the recommended follow-on integration.

## Run locally

Requires Python 3.11+ and no runtime dependencies (the optional extras for the later experiments are listed in the [README](../README.md#run-the-local-experiments)). From the repository root:

~~~sh
python -m pip install -e . pytest
agent-movement demo          # or: python -m agent_movement.demo
python -m pytest -q          # all tests: agent_movement + corpus tooling
~~~

`agent-movement` is the package's one console script. Its subcommands (`demo`, `a2a-demo`, `peer-demo`, `relocate`, `bench`, `receipts`, `version`) forward their arguments unchanged to the existing `python -m agent_movement.<module>` entry points, which keep working. A missing optional extra gives an install hint and exit 2. See the [CLI reference](cli.md).

The demo starts an ephemeral localhost-only HTTP receiver as a **separate operating-system process** (`agent-b`), sends from `agent-a`, repeats the same request, tries a denied approval, and tests a stale-worker fenced commit. It then revokes the approval at runtime ([issue #38](https://github.com/MSKazemi/agent-movement/issues/38)): the parent plays a synthetic user authority, provisions its HS256 test key to the receiver in a 0600 file, commits one simulated effect of the delegated task, has a forged, an unsigned and a wrong-purpose notice refused (HTTP 401), revokes with a signed notice (200, then 200 `replayed: true`), and shows that a new handoff, a replay and the task's next simulated effect are all denied. All task data are synthetic; SQLite is stored in a temporary directory and removed afterward. Output includes a completed word count, replay detection, HTTP 403 denial, a successful new-epoch simulated commit and the `revocation` results. The process exiting cleans up only the demo's own child process and temp data.

For manual testing in another terminal, run `python -m agent_movement.http --db /tmp/agent-movement-demo.sqlite --port 0`. It prints the actual loopback port on stdout. **Do not run behind a public proxy or forward this port.** The receiver allows exactly one sample task reference (`demo-task`), one origin claim (`agent-a`), and one task type by default. Its policy entry expires after ten minutes. `--revocation-authority FILE` pins the key (or list of keys, in the `agent_movement.trust` export format) whose signed notices `POST /v0/revocations` accepts; without it every notice is refused. An HS256 entry is a shared secret, so keep the file private.

Signed receipts on this path are **off by default**. With the `signing` extra, `python -m agent_movement.demo --receipts OUTDIR` signs the dispatch, the receiver's accept/reject and the fenced effect commits with ephemeral synthetic keys, writes `OUTDIR/live-run/` plus a separate `OUTDIR/trust-anchors.json`, and verifies the bundle offline; the receiver alone takes `--receipts-log FILE`. Without the flag the demo output is unchanged. See [live receipts](movement-receipts.md#live-http-path-issue-32).

## Contract, failure handling and evidence

- `src/agent_movement/core.py`: strict `0.1.0-draft` typed JSON envelope, allowlisted task kinds (`word_count`, `sha256`), UTF-8 size bounds and unsupported/extra-field denial. This is not a normative standard.
- `HandoffReceiver`: validates the destination claim and a receiver-local scoped `Approval` before performing an **allowlisted, pure** text calculation. Agent IDs are **claims, not authenticated workload principals**. `Approval.revoked` is a **static configuration flag** fixed at construction; runtime revocation is the separate API below.
- **Runtime revocation ([issue #38](https://github.com/MSKazemi/agent-movement/issues/38)).** `HandoffReceiver.revoke(notice)` and `POST /v0/revocations` accept a signed revocation notice in the [peer-authentication](peer-authentication.md) format (`trust.issue_revocation(authority_key, approval_ref, revoked_at)`; its `grant_id` names the approval). The notice must verify against a revocation authority pinned at construction (`revocation_authorities=`: an HS256 test key, or a public-only Ed25519 key with the `ed25519` extra). Unsigned, forged, tampered, wrong-purpose, untrusted-issuer and malformed notices are refused (`RevocationRejected`, HTTP 401) and audited as `approval.revocation_rejected`; a verified notice for an approval this receiver does not hold gets 404. A verified notice is recorded in `approval_revocations` and audited as `approval.revoked`. It takes effect when its write transaction commits: the admission check runs inside the delivery transaction, so new **and replayed** handoffs under the approval are denied (`ApprovalRevoked`, HTTP 403, `handoff.denied`). Revocation is idempotent: a repeat, or a later notice for the same approval, returns `replayed: true` and records nothing new; there is no un-revoke. The notice's `revoked_at` is the issuer's claim and is kept only for the record. With receipt emission on, the receiver signs one `authority.revoked` receipt per applied revocation (see [movement receipts](movement-receipts.md#live-http-path-issue-32)). Any pinned authority can revoke any of the receiver's approvals; with HS256 the receiver holds the secret too, so it could revoke its own approvals (revocation only ever removes authority).
- `SQLiteStore`: transactional deduplication by operation idempotency key and movement ID, atomic result/receipt persistence, and audit events containing only IDs and digests (no raw task text). Concurrent exact retries are answered with `replayed: true`. Since [issue #29](https://github.com/MSKazemi/agent-movement/issues/29), idempotency keys are scoped to their sender: the deduplication key is `(sender, idempotency_key)`. The sender is the authenticated origin when the caller knows it (the [peer path](peer-authentication.md)) and otherwise the envelope's *claimed* origin. `HandoffReceiver` authenticates nobody, so on that path the scope is only as strong as the origin claim. Two approved senders can now use the same key; before, the second one got 409. Movement IDs stay unique across all senders, so reusing another sender's movement ID is still a conflict, and that 409 still reveals that the ID exists.
- **Keyed commitments and retention (issue #39).** Since store layout version 2, every content digest the store writes (envelope, artifact, effect payload; also in the peer and A2A tables of the same file) is an HMAC-SHA256 commitment under a random per-store secret, so the file's audit export and logs cannot confirm a guess of low-entropy task text. Equal inputs still commit equally within one store, so replay and conflict detection are unchanged. The stored receipt drops its content-derived fields, and a replay recomputes them from the presented envelope. Opening a version-1 file migrates it in place, once, in one transaction, and there is again no downgrade path. `agent-movement purge --db FILE --older-than 30d` deletes old history rows and audits the purge, but keeps owners/epochs, effect ledgers, revocations and anything a live grant or an in-flight admission needs. Purging `deliveries` ends the retry window for those deliveries. See [data retention](data-retention.md).
- **Store migration (issue #29).** The file layout is versioned in `PRAGMA user_version` (`STORE_SCHEMA_VERSION = 1` at the time; 2 since issue #39). Opening a file in the unversioned PR #6 layout (version 0, `deliveries` keyed by the key alone) migrates it in place: one `BEGIN IMMEDIATE` transaction rebuilds `deliveries` with the SQLite create-copy-drop-rename procedure and takes each row's sender from its stored receipt's `origin_agent_id`. That value is exact, because on both receiver paths the envelope origin is the sender. Retries of pre-migration deliveries keep replaying their stored receipts. Concurrent openers serialize on the lock, so the migration runs once. A row whose receipt names no valid origin aborts the migration with `StoreSchemaError` and leaves the file unchanged. A file with a *newer* version is refused. There is no downgrade path: older code cannot record a new delivery in a migrated file (its four-column `INSERT` fails), so back up the file before upgrading if you might roll back.
- `EffectGateway`: separate simulated ownership table with monotonically increasing epochs; an old worker cannot commit after a transfer because the gateway checks the epoch in the same SQLite transaction as its effect record. This is **not** an exactly-once guarantee for third-party tools, nor an actual runtime checkpoint. Since issue #38 the same transaction also rechecks runtime revocation: each new delivery binds its task to the approval that admitted it (`task_approvals`), and a commit for a task with a revoked approval is refused (`ApprovalRevoked`, audited as `effect.denied`), replays and commits by a later owner after a transfer included. Revocation and commits take the same SQLite write lock, so whichever commits first wins; a revocation does not undo an effect committed before it. Limits: a task that never arrived through a `HandoffReceiver` delivery carries no approval and is only epoch-fenced; deliveries recorded before this change carry no binding; expiry is not rechecked at commit (the gateway does not hold the approvals); and the check is only as good as the cooperation of this simulated gateway.
- `HTTP` boundary: loopback-only, intentionally simple HTTP+JSON, with input validation and bounded sizes. It does **not** provide TLS, sender authentication or user identity proof for handoffs. The only signature it verifies is that of a revocation notice on `POST /v0/revocations`, against the locally pinned authority. Do not expose across trust domains.
- `demo.py`: end-to-end out-of-process experiment; no model API keys, third-party accounts, browser sessions or physical devices involved.

A receipt includes transfer identifiers, a content digest, a deterministic result artifact/digest, and a caller-supplied trace correlation ID. This receipt itself is unsigned, so it must not be described as cryptographic proof of an agent's identity or behavior. The digests in the receipt the sender gets are unsalted and cover the task text; the store itself keeps only keyed commitments to them ([data retention](data-retention.md)). A separate experiment, [signed movement receipts](movement-receipts.md), adds Ed25519-signed receipts over salted commitments, independent tool-side records and an offline verifier with synthetic fixtures; with `--receipts` the demo emits such receipts from this live path as well. A signature still does not make a statement true.

## What the tests establish

Test totals on 2026-10-16 (`python -m pytest -q`, which also runs the corpus-tooling tests): **351 passed, 1 skipped** with every optional extra installed (CPython 3.11.16 and 3.13.15), and **276 passed, 76 skipped** with the core only (CPython 3.13.15 and 3.15.0rc2). The skipped tests are those that need a missing extra. CI runs both configurations in [`python-smoke.yml`](../.github/workflows/python-smoke.yml).

The committed unit/integration tests for this slice cover: structural contract validation, duplicate JSON keys, rejected task kinds/classifications, wrong/expired/revoked approvals, serial and concurrent replay safety, receipt persistence after re-opening a DB, conflicting reuse of operation/movement identifiers, the same key used by two senders, the version-0 store migration (including six processes opening one legacy file at once), local HTTP status codes, epoch fencing after ownership transfer, and concurrent duplicate simulated effects. `tests/test_runtime_revocation.py` (issue #38) covers a revocation between admission and effect commit blocking the commit, forged, unsigned, tampered, wrong-purpose and unpinned notices being refused, idempotent and concurrent revocation, persistence across store instances, the HTTP endpoint and its status codes, the `authority.revoked` receipt, and the stated scope limit (a task without a delivery is only epoch-fenced).

**Scope limit:** There is no injected coordinator crash matrix, real cross-machine run, A2A interoperability check, model continuation measurement, tool authorization boundary outside the simulated gateway, or verified production-security claim.

## Next engineering and scientific issues (ordered)

1. **Real A2A v1 integration:** build an opt-in official-SDK adapter and independent sender/receiver, pin supported SDK and spec versions, test against the A2A inspector and a second implementation. Keep the transfer application profile separate from A2A message framing. *A first slice (official `a2a-sdk` 1.2.2 on both ends, two local processes) is in [a2a-adapter.md](a2a-adapter.md), and its wire profile is specified in [a2a-profile-extension.md](a2a-profile-extension.md) (resolvable extension URI, server-generated `contextId` by default). The official A2A TCK and the Inspector validators have been run against it (results and documented deviations in the [adapter doc](a2a-adapter.md#conformance-official-a2a-tck-and-inspector)), and an `@a2a-js/sdk` client completes handoffs against the Python server; other SDKs and the reverse direction are untested.*
2. **Pre-disclosure authorization:** authenticate peer identity, verify recipient and authority *before transmitting task content*, negotiate capabilities, issue expiring audience-bound approvals, and enforce revocation at the action boundary. Local untrusted agent_id strings are insufficient. *A first synthetic, local slice (signed cards, scoped grants, metadata-only preflight, commit-time revocation recheck) is in [peer-authentication.md](peer-authentication.md). The PR #6 core receiver accepts the same signed revocation notices at runtime and rechecks them at its simulated effect commit (issue #38), but still authenticates no sender. With the optional `hpke` extra, deliveries and receipts are HPKE-sealed to a CA-signed receiver key, so an on-path relay sees only ciphertext (issue #19). The stdlib-only mode has no confidentiality. TLS/channel binding and A2A integration remain open.*
3. **True same-runtime checkpoint relocation:** integrate one pinned durable agent runtime (e.g. LangGraph), specify safe checkpoint boundaries, transfer task ownership and continue on a second worker; persist and reconcile out-of-band effects. *A first synthetic slice with pinned LangGraph is in [checkpoint-relocation.md](checkpoint-relocation.md); its two-store mode copies the checkpoint into the receiver's own store as a digest-verified bundle, with only the coordinator still shared. Opaque effects whose outcome is unknown are parked and resolved by an [operator decision](checkpoint-relocation.md#operator-reconciliation-of-parked-effects-issue-30) (`confirmed_done` or `confirmed_absent`), fenced by the ownership epoch and audited; correctness rests on the operator's out-of-band check.*
4. **Fault injection:** kill origin, receiver and coordinator at every state transition; add delayed acknowledgements, lost replies, forged recipients, partitions, cancellation and external effect states marked `unknown/reconcile` rather than assuming failure. *Partly covered by the 30-row crash/duplicate/version fault matrix the 11-row two-store copy fault matrix and the 9 operator-reconciliation rows in [checkpoint-relocation.md](checkpoint-relocation.md), and by [MobilityBench v0.2](mobilitybench-v0.2.md), which crashes executors inside effect steps and drops a request, loses a reply or delays a request between origin and destination for every applicable baseline.*
5. **MobilityBench:** publish versioned synthetic datasets, the keep/restart/delegate/relocate baselines, per-run quality/cost/safety measures, reproducible seed manifests and negative findings; align with the companion [scientific agenda](strategic-target-and-scientific-agenda.md). *A first frozen, LLM-free pilot is [MobilityBench v0.1](mobilitybench-v0.1.md); its A2A and relocation baselines are scored only when their optional extras are installed (otherwise reported as unavailable), and reconstruction is always reported as unavailable. [MobilityBench v0.2](mobilitybench-v0.2.md) adds mid-step crashes, partitions and a stable-ID restart baseline as a separate frozen release.*
6. **Independent forensics and evidence:** signed/verified transfer receipts, an audited event-store design, independent tool-side attestations and redaction/retention tests before claiming provenance assurance. *A first slice with synthetic fixtures is [signed movement receipts](movement-receipts.md).*
